# Design decisions

Decisions made after the proposal, where the proposal left room. Code must follow these.

| # | Date | Area | Decision | Why |
|---|---|---|---|---|
| D1 | 2026-11-12 | Score (§7.5) | A finding the **creator rejects** still deducts. Only reviewer/owner **dismiss or waive**, or a new version where the issue is gone, removes the deduction. | Creators can't raise their own score or bypass the approval gate (§8.1). The rejection reason is shown to the reviewer. |
| D2 | 2026-11-12 | Confidential Guard | Match registered internal terms as **whole words**, case-insensitive, with any run of spaces/hyphens/underscores/line breaks between words. "Project Atlas" catches `PROJECT-ATLAS`, `project  atlas`; does not catch `Atlassian`. The same matching sees through hidden-codename tricks (found in a red-team review and confirmed by a test): zero-width characters and soft hyphens inside a word, Unicode dashes, full-width letters and Cyrillic or Greek lookalikes (`Pro\u200Bject Atlas`, `Pr\u043Eject Atl\u0430s`). Matching runs on the original text, so offsets stay valid for the AI step; the lookalike table is a fixed list of common letters. | Avoid false Criticals that block approval. Owners should register specific names ("Project Atlas"), not generic words ("Atlas"). |
| D3 | 2026-11-12 | Evidence validator (§7.3) | If the AI's quote exists **anywhere** verbatim in the content, keep the finding and **correct the offsets** to the occurrence nearest the stated offset. Discard only if the quote does not exist at all. | Models miscount characters; the verbatim quote is the real evidence. |
| D4 | 2026-11-12 | Contrast on images | Extract dominant colours from the image and check the lowest-contrast pair among the three most common colours that cover at least 5% of the image (anti-aliasing blends are not colours anyone chose). Pixels cannot say which colour is text, so this is a guess: **low** confidence, labelled "Needs human check", no score deduction. On the clean demo banner the guess pairs the teal graphic with the background and is only a note. If the creator enters text + background colours on the upload form, check those exactly (**high** confidence). | Keeps contrast a measurable code check (§9.1); the precise, scored check is the one from typed colours. |
| D5 | 2026-11-12 | Wording rule pack | Hype, absolute-claim, vague-source and AI-phrasing checks come from MIT rule sets (vale-ai-tells, marketing-machine), generated into `src/lib/rules/packs/marketing-en.json` by `scripts/build-rulepack.py`. Every pack finding is **medium** confidence with no auto-fix; owners can switch rules off (`disabledPackRules`). `PACK-AI-VOCAB` is **info** (no score impact): on a human-written 62-page PDF it fired 11 times on ordinary words ("significant", "crucial"). | A phrase match is a signal, not proof (§7.4). Medium keeps the score impact small (minor = 1.8) so a reviewer dismissal, not the creator, decides. |
| D6 | 2026-11-12 | System rule codes | Findings not tied to an org clause/fact/term use fixed codes: `WCAG-1.4.3`, `WCAG-1.1.1`, `READABILITY`, `BRAND-PALETTE`, `BRAND-FONTS`, `PACK-*`. Stored in `findings.rule_code` (migration `20261112000300_audit_persistence`). | `brand_assets` has no code column and WCAG/pack rules are not org data, but every finding must still name its source (§7.3). |
| D7 | 2026-11-12 | Web-page fetch | DNS is resolved and every address checked before each request and redirect (max 3); http/https on ports 80/443 only; 2 MB / 10 s limits; HTML only. Shortcut: no protection against DNS rebinding between lookup and connect. | Covers the SSRF cases in PLAN.md (Testing); full rebinding protection needs a custom dispatcher, out of MVP scope. |
| D8 | 2026-11-12 | Image colours | Dominant colours are computed with `sharp` (96 px, 8 levels per channel, mean colour per bucket, pixel share) instead of node-vibrant. | Palette and contrast checks need each colour's share of the image; the result is deterministic, so the same image always gives the same findings. |
| D9 | 2026-11-12 | DB tests | Migrations, RLS and `save_audit()` are tested on **PGlite** (in-process Postgres) with a small Supabase shim (`tests/db/harness.ts`). The hand-run SQL suites (19 RLS + 7 gate) now run in CI. | No Docker or Supabase project in CI; the shim mirrors Supabase's roles, grants and `auth.uid()`. Full Supabase (Auth, REST, Storage) is still checked with `supabase start`. |
| D10 | 2026-11-12 | `/api/audit` | The item and version are created with the **user's** client (RLS decides who may submit); knowledge is read and the run saved with the **service** client through `save_audit()`, one transaction. AI skipped/failed is stored as `mode = 'rule_only'`. `today` is the date in India (Asia/Kolkata). Shortcuts: uploaded files are not yet kept in Storage (`file_path` empty), and there is no per-org daily AI cap yet (§11.5). | Creators must not be able to write runs or findings themselves, and the Confidential Guard needs internal terms the creator can't read. |
| D11 | 2026-11-12 | UI data access | Pages read only through the user's RLS client (`getViewer()`); no page uses the service key. The item page recomputes the score from the findings' current statuses with the same formula (§7.5), so dismissals/waivers show at once; the run's stored score stays the score at audit time. Cited facts/terms a creator may not read show as "restricted". | One source of truth for permissions (RLS), and the Confidential Guard's internal register never reaches a creator's browser. |
| D12 | 2026-11-12 | Sign-in | Email + password via Supabase Auth, session refreshed by `src/middleware.ts`; signed-out users are sent to `/login?next=…`, and `next` must be a same-site path (`safeNext`). | Magic links need email delivery set up; password sign-in works on a fresh project. Open-redirect protection for the post-login hop. |
| D13 | 2026-11-13 | Apply fixes (§8.2) | `POST /api/items/:id/apply-fixes` applies every **accepted** finding's suggestion on the item's latest version, as the user (RLS), into a new version that is re-audited. Overlapping fixes keep the earlier one; a fix whose quote no longer matches is skipped with a reason. The new version is re-audited as plain text. | Matches "creator revises → new immutable version → re-audit" (Figure 7). Files are not kept in Storage yet (D10), so file-level checks (fonts, images) are not repeated on fixed versions. |
| D14 | 2026-11-13 | Errors in the review UI | Database errors are mapped to fixed sentences (`friendlyDbError`); raw Postgres/PostgREST text is never shown. The approval-gate message is rephrased with its count. | Same rule as the API routes: internal error text stays internal. |
| D16 | 2026-11-14 | Clause versions (P2) | Changing a clause's text keeps the old text in `guideline_clause_history` and bumps `version` in a database trigger; the client never sets the version, code, category or org. Status changes do not create a version. | §8.3 "guidelines change only when the owner saves a new version"; older findings can still be read against the rule as it was. |
| D17 | 2026-11-14 | Knowledge Centre (P2) | Owners add and edit clauses, facts, terms and assets in the browser under RLS (owner-only writes, tested). Facts and terms are edited, not deleted, because findings and claim links reference them; assets can be removed. Vale `.yml` files import as terms with code prefix `VALE-<file name>`; terms already present are skipped. "Expired" uses India time, like the audit. | Same permission model as the review loop; no service key in the browser. Importing the same file twice adds nothing. |
| D18 | 2026-11-14 | AI time budget | The AI gets ONE budget per audit, retry included (`AI_BUDGET_MS` = 45 s, Azure request cancelled at 45 s). A retry after invalid output starts only if at least 10 s are left. A test checks the budget leaves ≥ 10 s of each route's `maxDuration` (60 s). Replaces `feature/ai-timeout` (60 s + 70 s per attempt, up to 140 s with a retry). | gpt-6-luna can need more than 25 s, but a 60 s Vercel function killed at the limit returns a 504 instead of rule-only results (§9.1). |
| D15 | 2026-11-13 | Azure region | The AI model runs in a separate Foundry project in **Southeast Asia** (`inkloom-sea`), deployment `gpt-6-luna`, **Global Standard**. Demo and the public site use `DEMO_MODE=true` (recorded results, no Azure cost). | gpt-6-luna is not offered in Central India, and the student subscription's policy blocks South India. Global Standard may process requests outside the region; stored data stays with the resource. Only masked public content and public brand rules are sent (§10.1). |
| D20 | 2026-11-14 | Cost control (§9.1) | The public site runs the real model for judges on shared demo accounts, so audits are limited: one account may start 20 audits in 10 minutes (`AI_BURST_MAX`; over that the request is refused with 429 before anything is stored) and the organisation may run 3000 real-model audits per 24 hours (`AI_DAILY_CAP`; over that audits still work on the rule checks only, with a note, so the site never goes dark). Counted from `audit_runs`, no new table. An audit costs about Rs 0.07, so the limits stop a script, not judges. | Both audit routes (`/api/audit`, `/api/items/:id/apply-fixes`) use `gateForRequest` in `src/lib/audit/usage-cap.ts`. A counting error lets the audit run and is logged. Not counted: the Brand Health AI buttons (owner and reviewer only), and a few simultaneous requests can slip past the count. |
| D19 | 2026-11-14 | Brand Health (§8.3, P5) | Four detectors are pure functions (`src/lib/health/detectors.ts`): recurring mistakes per rule over 30 days, counted as posts that broke the rule (a post counts once per rule however many versions repeat the mistake; dismissed and waived findings are not mistakes; a creator's rejection still counts, D1), unclear rules (dismissed or waived in at least 40% of at least 5 decisions), conflicting terms (deterministic, always on), and fact impact. Two actions call the model on request, owner and reviewer only, and save nothing: "Suggest a rewrite" for an unclear rule (a draft from the clause and the reviewers' dismiss reasons; it is rejected if it adds a number that is not in the rule or the notes) and "Compare rules with AI" for contradicting clauses (only pairs of two different active clauses of one category are kept). Without the real model the rewrite uses one recorded draft, labelled Simulated, and the comparison says it needs the real model instead of claiming there are no conflicts. Fact impact needs to know which content relies on a fact, so every audit now stores a claim link for each fact the content restates (all of the fact's figures appear, `linkFacts`), not only for findings that cite a fact; `approved_facts.updated_at` marks when a fact last changed (migration `20261114100000`). The page aggregates in the server from the viewer's RLS client, up to 5000 findings; move the counting into SQL when an organisation outgrows that. Charts are plain HTML bars with a table, so no chart library was added. Tests never call the model. |
| D21 | 2026-11-14 | AI output is re-checked (red-team review) | A model's suggested fix is dropped, with a note on the run, if it contains a banned term or an internal term (same matching as the Guard); the finding stays. A Brand Health rewrite draft is rejected for an internal term, or a banned term the current rule did not already mention. What the Brand Health buttons send to the model (rule text, reviewers' quotes and reasons) is masked for internal terms and personal data like every audit. | Without it the model could reintroduce a banned term, and reviewers' quotes of real content could carry a codename to the model. Code: `src/lib/rules/suggestion.ts`, `src/lib/audit/pipeline.ts`, `src/app/api/health/*`. Not done: stopping approval of an older version once a newer one exists (approval gate, needs the owner's decision). |

## D22 · Model prompt tightened after the first real-model eval (15 Nov 2026)
First `npm run eval -- --ai` with prompt v1-draft: recall 86.6%, high-confidence precision 66.7% (target 85%). Most wrong high-confidence findings were "messaging" findings on ordinary opening sentences, and number mismatches filed as "claim". Prompt v2-eval adds four rules (numbers that contradict a fact are "factual"; when unsure return nothing; messaging needs a specific clause; no terminology findings from the model). Result: recall 83.6%, high-confidence precision 95.1%, clean cases with a finding 6 of 12 down to 3 of 12. We accepted a small loss of recall for precision. Both runs are kept in `eval/results/`. The same run showed a gap: internal facts (FACT-90, FACT-91) restated in public copy were not detected (see D23).

## D23 · Confidential Guard also checks internal facts (15 Nov 2026)
The eval showed 5 of 5 internal-fact leaks missed: the Guard only knew internal terms. `findInternalFactLeaks` (src/lib/guard/internal-facts.ts) flags public copy that (1) repeats an internal fact's significant figures together with at least half of its other words close by, or (2) uses the name an internal fact starts with ("Northbeam Mobile") when no public rule, fact or term uses that name. Both give a Critical, high-confidence confidentiality finding, and the leaked span is hidden from the model like codenames. Limit: a paraphrase with neither the figures nor the name is not caught. Result on the eval set: internal-fact recall 0% to 100%, no new false positive on the 12 clean cases (rules-only and with the real model; AI run: recall 97%, high-confidence precision 97.7%).

## D24 · Better guess of text colours in images, and rewording of internal facts (15 Nov 2026)
**Image contrast (refines D4).** With no colours typed on the upload form, the image is now scanned for its main background and for every solid foreground colour (anti-aliasing blends are skipped); the foreground with the lowest contrast on that background is checked. The old guess only looked at colours covering 5% or more of the image and missed thin text: on the demo low-contrast banner the pale teal headline covers under 1%. The result is still a guess without OCR, so it stays LOW confidence (no score deduction, "Needs human check"); typed colours stay the precise path. An icon or logo can be reported like text.
**Internal facts reworded (extends D23).** The Guard also flags the same figure in other notation (12,000 / 12k / 12 thousand) with related words (word family and a small synonym list) as a medium-confidence "needs human check" hint. Still not caught: a paraphrase with neither the figure nor the name, and spelled-out numbers ("twelve thousand"). Catching those needs a semantic model that sees internal facts, which the product promises never to do.

## D25 · Uploads and logos are kept in private Storage (15 Nov 2026)
Migration 20261115100000: `content_versions` gets `file_name` and `file_type` (`file_path` already existed); two private buckets. `content-files/<org>/<version>/<file>`: written only by the audit route with the service role (best effort, a storage problem never fails an audit), read through a policy that asks whether the caller can see the version (so it follows the same content-item rules as the text). `brand-assets/<org>/<asset>/<file>`: members read, only the owner uploads, replaces or deletes; PNG, JPG or WebP up to 2 MB, type checked on the bytes, no SVG. Pages use signed links that expire (10 minutes for originals, 1 hour for logos). Tested in tests/integration/storage.test.ts on the in-process database with a small Storage shim. Logos are stored and shown, not yet used by any check. Supabase refuses to delete storage objects from SQL, so the nightly demo reset leaves uploaded files behind; they cannot be opened once their post is gone. Checked on the live site: a logo upload, preview and removal (file removed too), and an image audit with "Open original" and the preview.

## D26 · Brand-book import (P2b) (15 Nov 2026, Raghav)
`POST /api/knowledge/import` (owner only) parses a PDF/DOCX and asks the model for a DRAFT of guidelines, terms and colours; it saves nothing. Every drafted item must quote the document: items whose quote is not found are dropped, and `source_page` comes from where the quote sits in the parsed text, not from the model. Codes come from `nextCode`, never from the model. The owner edits, keeps or discards each item; kept items are saved with the owner's own session under RLS. Demo mode uses a recorded draft for `seed/northbeam/brandbook.pdf`; it was written by hand from the parsed text (no Azure key while building) and can be replaced with a real answer via `RECORD_IMPORT=1`. Shortcut: imports are not counted by the usage cap.

*Why:* §5.1 "import guidelines"; same grounding rule as the evidence validator (§7.3); the AI never writes to the database.

## D27 · Deleting facts (15 Nov 2026, Raghav)
Owners can delete a fact only while no finding cites it (the `findings.fact_id` reference refuses the delete, 23503); a cited fact is retired with "Valid until" instead.

*Why:* Past findings must keep the source they cited (§7.3).

## D28 · Big files go straight to Storage (15 Nov 2026)
Vercel refuses request bodies over about 4.5 MB (413 FUNCTION_PAYLOAD_TOO_LARGE) before our code runs, so a 5 MB brand book or PDF failed with a misleading message although the app allows 10 MB. Files up to 4 MB are still sent with the form. Bigger ones: the browser asks `POST /api/upload-url` for a one-time signed upload into `content-files/staged/<user>/<random id>/<file>`, uploads there directly, and sends only the path; the audit and import routes accept a path only from the caller's own staging folder (`isStagedPathOf`), fetch it with the service role, delete it, and carry on as for a normal upload (`src/lib/storage/staged.ts`). Users cannot read staged files (the bucket's read policy needs a version that points at the file). Also: the brand-book draft now checks each item on its own, so one malformed item from the model is dropped with a note instead of losing the whole draft (seen once on a 30-page brand book).

*Why:* brand books are often over 5 MB, and judges upload their own. Shortcut: a staged file that is never submitted stays in the bucket; add a cleanup job if storage use grows.

## D29 · The app runs on Azure App Service (15 Nov 2026)
`inkloom-specfix` (resource group `inkloom-web-rg`, Linux B1, Central India next to Supabase in Mumbai, Always On, HTTPS only, Node 24). It runs the same code against the same Supabase project and model. Azure has no 4.5 MB body limit and no 60 s function limit (its front end allows about 230 s), so it is the safer host for big brand books. Building on App Service was too slow on B1 (npm install alone took 9 minutes), so `scripts/build-azure.sh` builds a standalone bundle locally (`NEXT_OUTPUT=standalone`, Linux binaries for sharp added) and it is deployed as a zip; start command `HOSTNAME=0.0.0.0 node server.js`; keys live only in the App Service settings. Azure is now the only host: the earlier Vercel deployment is retired and the repo no longer refers to it (`vercel.json` removed). `.github/workflows/deploy-azure.yml` deploys every push to `main` (tests, then `scripts/build-azure.sh`, then `azure/webapps-deploy` with the app's publish profile as a GitHub secret, then a check that `/login` answers); FTP stays off.

*Why:* the event is judged once from a link; large uploads and long AI steps must not fail because of a host limit. Shortcut: deploys are manual (`az webapp deploy`), not from GitHub; add a GitHub Actions workflow if Azure becomes the main host.

## D30 · Sign-in callback redirects are relative (15 Nov 2026)
Found by Udit's sign-up test on Azure: a confirmation link that failed (`otp_expired`) opened `https://0.0.0.0:8080/login`. Behind Azure App Service the Node server only sees its inner address (`HOSTNAME=0.0.0.0`, `PORT=8080`), so `new URL("/login", req.nextUrl.origin)` in `/auth/callback` produced an address nobody can open. The callback now answers 307 with a relative `Location`, which the browser resolves against the address it really used and which keeps Supabase's `#error=...` fragment. The middleware redirect was already relative (checked on the live site). Test: `src/app/auth/callback/route.test.ts`.

*Why:* sign-up and email links must work on the real host, not only on localhost. Shortcut: the login page does not yet turn the `#error` fragment into a readable message.

## D31 · Second labeller applied; new evaluation numbers (15 Nov 2026)
Shrikant Sharma (SS) read all 48 cases against `seed/northbeam/knowledge.json` (he used Claude for a second opinion; his full review is in `eval/second-labeller-SS.md`): 39 OK, 9 with changes. Udit accepted all nine and they were applied by script (`labelled_by` is now `["UB","SS"]` on every case): EV-FACTUAL-05 loses its duplicate factual label; "Stop babysitting files" (EV-TONE-04) and the jargon sentence in EV-MSG-06 are added as borderline minor tone labels; EV-ACC-01 is split into an alt-text finding and a contrast finding; the EV-TONE-05 messaging quote is shortened; the six MSG-01 labels go from major to minor and EV-ACC-05 from minor to major. The scoring ignores severity and rule id, so only the label changes that add or remove an issue move the numbers: 67 labelled issues became 69.

Results with the new labels (real model, two runs, because the model's answers vary): run 1 recall 88.4%, precision 77.1%, high-confidence precision 93.0% (one model call failed, so that case ran on rules only); run 2 recall 91.3%, precision 72.3%, high-confidence precision 87.8%. Rule checks alone: recall 52.2%, precision 79.6%, high-confidence precision 100%. Codenames and internal facts: 100% in every run. Before the second labelling (single labeller, 67 issues) the same prompt scored 97% recall and 97.7% high-confidence precision; the lower figures now come from the two added borderline labels, one failed call, and ordinary variation, and we report both.

*Why:* proposal §7.7 asks for two labellers, and publishing both runs is more honest than one favourable run. Files: `eval/results/rules+ai-run1.json` (run 1), `rules+ai.json` (run 2), `rules-only.json`, and the `*-before-second-labeller.json` files for the earlier labels. Shortcut: image labels match any accessibility finding on that image, so the two ACC-01 labels can both be hit by one finding.

## D32 · Web page input reads the main content only (16 Nov 2026)
A team test audited a Wikipedia article and got 23 findings and a -40 accessibility penalty: the parser read the whole page, including "Jump to content" and the site menus, and counted every logo and icon as an image without alt text. `parseHtmlContent` now removes `<nav>` and `role=navigation` everywhere, then reads only the page's `<main>` (or `role=main`), or its only `<article>`, when that holds at least 200 characters of text; otherwise it reads the whole body as before. Images are counted only inside the part that is read. Tests: four new cases in `src/lib/parsers/parsers.test.ts`; checked on python.org and example.com (clean) and on the Wikipedia article (menus gone, text starts at the article title).

*Why:* a judge is likely to try the "Web page" tab with a site they know, and an audit should be about the author's copy, not the site's chrome. Shortcut: a page with no `<main>` and several `<article>`s is read whole, and an article page with many unlabelled images can still reach the accessibility cap.
