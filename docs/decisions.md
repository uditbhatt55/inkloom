# Design decisions

Decisions made after the proposal, where the proposal left room. Code must follow these.

| # | Date | Area | Decision | Why |
|---|---|---|---|---|
| D1 | 2026-11-12 | Score (§7.5) | A finding the **creator rejects** still deducts. Only reviewer/owner **dismiss or waive**, or a new version where the issue is gone, removes the deduction. | Creators can't raise their own score or bypass the approval gate (§8.1). The rejection reason is shown to the reviewer. |
| D2 | 2026-11-12 | Confidential Guard | Match registered internal terms as **whole words**, case-insensitive, with any run of spaces/hyphens/underscores/line breaks between words. "Project Atlas" catches `PROJECT-ATLAS`, `project  atlas`; does not catch `Atlassian`. | Avoid false Criticals that block approval. Owners should register specific names ("Project Atlas"), not generic words ("Atlas"). |
| D3 | 2026-11-12 | Evidence validator (§7.3) | If the AI's quote exists **anywhere** verbatim in the content, keep the finding and **correct the offsets** to the occurrence nearest the stated offset. Discard only if the quote does not exist at all. | Models miscount characters; the verbatim quote is the real evidence. |
| D4 | 2026-11-12 | Contrast on images | Extract dominant colours from the image and check the lowest-contrast text-like pair (**medium** confidence). If the creator enters text + background colours on the upload form, check those exactly (**high** confidence). | Keeps contrast a measurable code check (§9.1) and keeps the demo's 3.1:1 banner finding. |
| D5 | 2026-11-12 | Wording rule pack | Hype, absolute-claim, vague-source and AI-phrasing checks come from MIT rule sets (vale-ai-tells, marketing-machine), generated into `src/lib/rules/packs/marketing-en.json` by `scripts/build-rulepack.py`. Every pack finding is **medium** confidence with no auto-fix; owners can switch rules off (`disabledPackRules`). `PACK-AI-VOCAB` is **info** (no score impact): on a human-written 62-page PDF it fired 11 times on ordinary words ("significant", "crucial"). | A phrase match is a signal, not proof (§7.4). Medium keeps the score impact small (minor = 1.8) so a reviewer dismissal, not the creator, decides. |
| D6 | 2026-11-12 | System rule codes | Findings not tied to an org clause/fact/term use fixed codes: `WCAG-1.4.3`, `WCAG-1.1.1`, `READABILITY`, `BRAND-PALETTE`, `BRAND-FONTS`, `PACK-*`. Stored in `findings.rule_code` (migration `20261112000300_audit_persistence`). | `brand_assets` has no code column and WCAG/pack rules are not org data, but every finding must still name its source (§7.3). |
| D7 | 2026-11-12 | Web-page fetch | DNS is resolved and every address checked before each request and redirect (max 3); http/https on ports 80/443 only; 2 MB / 10 s limits; HTML only. Shortcut: no protection against DNS rebinding between lookup and connect. | Covers the SSRF cases in PLAN.md (Testing); full rebinding protection needs a custom dispatcher, out of MVP scope. |
| D8 | 2026-11-12 | Image colours | Dominant colours are computed with `sharp` (96 px, 8 levels per channel, mean colour per bucket, pixel share) instead of node-vibrant. | Palette and contrast checks need each colour's share of the image; the result is deterministic, so the same image always gives the same findings. |
| D9 | 2026-11-12 | DB tests | Migrations, RLS and `save_audit()` are tested on **PGlite** (in-process Postgres) with a small Supabase shim (`tests/db/harness.ts`). The hand-run SQL suites (19 RLS + 7 gate) now run in CI. | No Docker or Supabase project in CI; the shim mirrors Supabase's roles, grants and `auth.uid()`. Full Supabase (Auth, REST, Storage) is still checked with `supabase start`. |
| D10 | 2026-11-12 | `/api/audit` | The item and version are created with the **user's** client (RLS decides who may submit); knowledge is read and the run saved with the **service** client through `save_audit()`, one transaction. AI skipped/failed is stored as `mode = 'rule_only'`. `today` is the date in India (Asia/Kolkata). Shortcuts: uploaded files are not yet kept in Storage (`file_path` empty), and there is no per-org daily AI cap yet (§11.5). | Creators must not be able to write runs or findings themselves, and the Confidential Guard needs internal terms the creator can't read. |
| D11 | 2026-11-12 | UI data access | Pages read only through the user's RLS client (`getViewer()`); no page uses the service key. The item page recomputes the score from the findings' current statuses with the same formula (§7.5), so dismissals/waivers show at once; the run's stored score stays the score at audit time. Cited facts/terms a creator may not read show as "restricted". | One source of truth for permissions (RLS), and the Confidential Guard's internal register never reaches a creator's browser. |
| D12 | 2026-11-12 | Sign-in | Email + password via Supabase Auth, session refreshed by `src/middleware.ts`; signed-out users are sent to `/login?next=…`, and `next` must be a same-site path (`safeNext`). | Magic links need email delivery set up; password sign-in works on a fresh project. Open-redirect protection for the post-login hop. |
| D13 | 2026-11-13 | Apply fixes (§8.2) | `POST /api/items/:id/apply-fixes` applies every **accepted** finding's suggestion on the item's latest version, as the user (RLS), into a new version that is re-audited. Overlapping fixes keep the earlier one; a fix whose quote no longer matches is skipped with a reason. The new version is re-audited as plain text. | Matches "creator revises → new immutable version → re-audit" (Figure 7). Files are not kept in Storage yet (D10), so file-level checks (fonts, images) are not repeated on fixed versions. |
| D14 | 2026-11-13 | Errors in the review UI | Database errors are mapped to fixed sentences (`friendlyDbError`); raw Postgres/PostgREST text is never shown. The approval-gate message is rephrased with its count. | Same rule as the API routes: internal error text stays internal. |
| D16 | 2026-11-14 | Clause versions (P2) | Changing a clause's text keeps the old text in `guideline_clause_history` and bumps `version` in a database trigger; the client never sets the version, code, category or org. Status changes do not create a version. | §8.3 "guidelines change only when the owner saves a new version"; older findings can still be read against the rule as it was. |
| D17 | 2026-11-14 | Knowledge Centre (P2) | Owners add and edit clauses, facts, terms and assets in the browser under RLS (owner-only writes, tested). Facts and terms are edited, not deleted, because findings and claim links reference them; assets can be removed. Vale `.yml` files import as terms with code prefix `VALE-<file name>`; terms already present are skipped. "Expired" uses India time, like the audit. | Same permission model as the review loop; no service key in the browser. Importing the same file twice adds nothing. |
| D18 | 2026-11-14 | AI time budget | The AI gets ONE budget per audit, retry included (`AI_BUDGET_MS` = 45 s, Azure request cancelled at 45 s). A retry after invalid output starts only if at least 10 s are left. A test checks the budget leaves ≥ 10 s of each route's `maxDuration` (60 s). Replaces `feature/ai-timeout` (60 s + 70 s per attempt, up to 140 s with a retry). | gpt-6-luna can need more than 25 s, but a 60 s Vercel function killed at the limit returns a 504 instead of rule-only results (§9.1). |
| D15 | 2026-11-13 | Azure region | The AI model runs in a separate Foundry project in **Southeast Asia** (`inkloom-sea`), deployment `gpt-6-luna`, **Global Standard**. Demo and the public site use `DEMO_MODE=true` (recorded results, no Azure cost). | gpt-6-luna is not offered in Central India, and the student subscription's policy blocks South India. Global Standard may process requests outside the region; stored data stays with the resource. Only masked public content and public brand rules are sent (§10.1). |
| D19 | 2026-11-14 | Brand Health (§8.3, P5) | Four detectors are pure functions (`src/lib/health/detectors.ts`): recurring mistakes per rule over 30 days (dismissed and waived findings are not mistakes; a creator's rejection still counts, D1), unclear rules (dismissed or waived in at least 40% of at least 5 decisions), conflicting terms (deterministic only; the AI clause-pair check is not built), and fact impact. Fact impact needs to know which content relies on a fact, so every audit now stores a claim link for each fact the content restates (all of the fact's figures appear, `linkFacts`), not only for findings that cite a fact; `approved_facts.updated_at` marks when a fact last changed (migration `20261114100000`). The page aggregates in the server from the viewer's RLS client, up to 5000 findings; move the counting into SQL when an organisation outgrows that. Charts are plain HTML bars with a table, so no chart library was added. |
